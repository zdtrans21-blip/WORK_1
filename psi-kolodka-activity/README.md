# psi-kolodka-activity

Кастомное активити дизайнера бизнес-процессов Битрикс24: распознаёт скан
протокола ПСИ (приёмо-сдаточные испытания) колодки локомотивной гребневой
через LLM с vision и записывает результат в поля смарт-процесса
«Показатели плавок» (`entityTypeId: 1068`, портал `aslz.bitrix24.ru`).

Отдельный самостоятельный проект — ничего общего с другими приложениями
в этом репозитории.

## Структура

```
index.js                    Express-сервер, роут POST /handler
install.js                  Регистрирует активити через bizproc.activity.add
handler.js                  Обрабатывает вызов активити из бизнес-процесса
services/
  bitrix.js                 Обёртка classic REST (crm.item.*, bizproc.event.send) + скачивание файла по urlMachine
  pdfProcessor.js            PDF → массив PNG-страниц (макс. 5)
  imagePreprocessor.js       pdftoppm/pdf2pic @300dpi + sharp-препроцессинг
  llm.js                     Запрос к LLM (OpenAI-совместимый или Anthropic формат)
  parser.js                  Разбор JSON-ответа LLM
  validator.js               Парсинг норм, вычисление отклонений факта от нормы
  fieldMapper.js              Результат → поля crm.item.update
prompts/psi_kolodka.js       Системный промт для LLM
scripts/testRecognition.js   Локальный тест на файле test-data/test-protocol.pdf
```

## Авторизация: два разных механизма

Регистрация активити (`bizproc.activity.add`) и повседневная работа
приложения используют **разные** источники авторизации в Битрикс24:

| Что | Авторизация | Как получается |
|---|---|---|
| `install.js` → `POST /v1/bizproc-activities` | OAuth-ключ приложения VibeCode `vibe_app_…` + сессия `Authorization: Bearer` | `POST /v1/apps` создаёт приложение и выдаёт ключ; сессию даёт разовая OAuth-авторизация администратора портала |
| `handler.js` во время выполнения БП | `auth.access_token`, который Битрикс24 сам присылает в каждом вызове активити | ничего получать не нужно — токен приходит в теле запроса |

**Важно (проверено на практике):** ни персональный API-ключ VibeCode
(`vibe_api_…`), ни обычный входящий вебхук уже установленного локального
приложения Битрикс24 **не подходят** для `bizproc.activity.add` — сам
Битрикс24 отклоняет оба варианта с `403 ACCESS_DENIED` /
`"Access denied! Application context required"`: методу нужен контекст
полноценного OAuth-приложения (`client_id`/`client_secret` + токен уровня
приложения), а не любой валидный REST-токен. Кроме того, сервер, на
который указывает `HANDLER`, обязан быть создан **тем же самым**
OAuth-ключом, которым идёт регистрация — иначе `400 SERVER_APP_MISMATCH`
(у каждого VibeCode-приложения может быть привязан только один сервер).
Поэтому и сервер (`POST /v1/infra/servers`), и регистрация активити должны
выполняться одним и тем же `VIBE_APP_KEY` + его сессией; для создания
сервера этому ключу дополнительно нужен скоуп `vibe:infra`.

Рабочий процесс (`handler.js`) при этом использует не ключ приложения, а
токен, который Битрикс24 передаёт в каждом конкретном вызове активити —
это менее привилегированный способ авторизации, не требующий отдельного
хранения секретов на время выполнения бизнес-процесса.

## Установка

```bash
npm install
```

## Деплой

1. Создайте OAuth-приложение VibeCode со скоупами
   `["crm", "bizproc", "disk", "vibe:infra"]` — `POST /v1/apps` (личным
   ключом), сохраните `rawKey` (это и есть `VIBE_APP_KEY`, показывается
   один раз).
2. Пройдите одноразовую OAuth-авторизацию этого приложения на портале —
   `GET /v1/oauth/authorize?app_key=...` → подтверждение администратором
   → `GET /v1/oauth/poll` до `status: complete`, получаете `session_token`.
3. Этим же ключом и сессией создайте сервер — `POST /v1/infra/servers`
   (нужен скоуп `vibe:infra`) — и задеплойте код —
   `POST /v1/infra/servers/:id/deploy` с архивом проекта в `source.content`,
   `runtime: "node20"`, `install: "npm install --omit=dev"`,
   `start: "node index.js"`. Платформа выдаёт публичный URL вида
   `https://app-xxxx.vibecode.bitrix24.tech` — это и есть `APP_URL`.

## Регистрация активити

1. Скопируйте `.env.example` → `.env`, заполните `VIBE_APP_KEY` и `APP_URL`
   (сервер из шага деплоя — обязательно привязанный к этому же `VIBE_APP_KEY`).
2. Запустите:
   ```bash
   node install.js
   ```
3. Скрипт выведет ссылку для одноразовой OAuth-авторизации, если сессии
   ещё нет (`VIBE_APP_SESSION_TOKEN` не задан) — откройте её под
   администратором портала `aslz.bitrix24.ru` и подтвердите доступ.
   Сессия действует 24 часа без продления.
4. При успехе активити `🔬 ПСИ Колодка: распознать протокол`
   (код `psi_kolodka_recognizer`) появится в дизайнере бизнес-процессов
   смарт-процесса «Показатели плавок».

## Настройка в дизайнере БП

Добавьте активити в процесс над элементом смарт-процесса «Показатели
плавок» и заполните параметры:

| Параметр | Значение |
|---|---|
| API URL провайдера LLM | например `https://api.openai.com/v1/chat/completions` |
| Модель LLM | например `gpt-4o` |
| API-ключ LLM | ключ провайдера (хранится только в памяти запроса, никуда не сохраняется) |
| Код поля с PDF протокола | код файлового поля смарт-процесса, откуда брать PDF, по умолчанию `UF_CRM_66_SOURCE_PDF` |
| ID элемента смарт-процесса | необязательно — по умолчанию активити сама берёт ID элемента, на котором запущен БП (из `document_id`, который Битрикс24 присылает при каждом вызове). Заполняйте, только если нужно распознать протокол другого элемента |

Возвращаемые значения (`ocr_status`, `ocr_warnings`, `error_message`)
доступны в следующих нодах процесса — например, для условного перехода
«если ocr_status = error, поставить задачу на ручную проверку».

## Локальный тест распознавания

```bash
cp .env.example .env    # заполните TEST_LLM_*
# положите тестовый протокол сюда:
#   test-data/test-protocol.pdf
node scripts/testRecognition.js
```

Скрипт сохранит обработанные страницы (`test-data/output-page-N.png`) для
визуальной проверки препроцессинга и выведет распознанный JSON вместе с
результатом валидации (норма/факт/отклонение).

## Известные особенности

- Поле `UF_CRM_66_SOURCE_PDF` только читается, никогда не перезаписывается.
- Файл в поле `UF_CRM_66_SOURCE_PDF` — это вложение смарт-процесса
  (crm dynamic item), а не классический файл Диска: `crm.item.get` отдаёт
  для него `{id, url, urlMachine}`, и `id` здесь — не Disk-файл-ID (`disk.file.get`
  с ним падает `ERROR_NOT_FOUND`). Скачивать нужно прямо по `urlMachine` —
  готовая ссылка на `crm.controller.item.getFile` с уже вшитыми `auth`/`token`.
- `bizproc.event.send` требует `auth` (access_token) в теле запроса —
  одного `event_token` недостаточно, без `auth` Битрикс24 отвечает
  `401 NO_AUTH_FOUND / Wrong authorization data`, и в журнал процесса
  ничего не попадает, даже сообщения об ошибках.
- Химсостав `Ca` присутствует в схеме ответа LLM (для контроля точности
  распознавания), но в смарт-процессе нет соответствующего `UF_CRM_66_CHEM_CA_*`
  поля — по заданному маппингу это значение не записывается в Битрикс24.
  Если нужно хранить и его — добавьте поле в смарт-процесс и маппинг в
  `fieldMapper.js`.
- Для микроструктуры Битрикс-поля есть только для нормы/факта — отдельного
  поля отклонения нет (в отличие от химсостава). `validator.js` всё равно
  считает статус по каждому параметру микроструктуры для журнала процесса.
- `bizproc.event.send` вызывается всегда, даже при ошибке на любом шаге —
  иначе процесс зависнет в статусе ожидания навсегда.
